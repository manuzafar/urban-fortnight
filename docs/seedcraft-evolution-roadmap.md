# Seedcraft Evolution Roadmap

> From sequential pipeline to intelligent multi-agent system with rich, presentation-ready outputs.

---

## Current State Assessment

Seedcraft is a solid Phase 1 MVP. Here's what's working well and where the gaps are:

### Strengths
- **Well-structured agent pipeline** — 6 agents with clear responsibilities and Pydantic schemas
- **Quality gates at two levels** — PRD sub-workflow (0.75 threshold) and overall critique (0.7 threshold) with up to 3 revision loops
- **Google Search grounding** already enabled on Customer Research, Business Strategy, and Legal agents
- **Real-time SSE streaming** gives users visibility into agent progress
- **Clean separation** — FastAPI backend, React frontend, LangGraph orchestration, Supabase persistence
- **Production infrastructure** — JWT auth, RLS, PDF/DOCX export, Railway deployment

### Gaps to Address
1. **Sequential bottleneck** — All 6 agents run in strict sequence (~8-10 min total). Customer Research must finish before Business Strategy can start, even though they have partial independence.
2. **Revision is a sledgehammer** — When critique fails (< 0.7), the ENTIRE pipeline re-runs from Customer Research. No targeted re-runs of weak sections.
3. **No cross-run learning** — Every session starts from zero. The system doesn't learn what "good" looks like across runs.
4. **Flat output format** — The inception pack is a JSON blob stored in `pack_data JSONB`. The frontend renders it, but there's no interactive exploration, no visual artifacts generated by agents.
5. **Single model for everything** — Gemini 2.0 Flash handles all agents. Some tasks (critique, business strategy) need deeper reasoning; others (formatting) need speed.
6. **No planning intelligence** — Every product idea gets the same agent pipeline regardless of domain, complexity, or what the user actually needs.
7. **Grounding is broad, not targeted** — Search grounding is on/off at the agent level, not query-specific. The research agent doesn't construct specific searches for competitors or market data.

## Phase 1: Surgical Improvements (1–2 weeks)

**Goal:** Maximise output quality with minimal architectural changes. These are changes to agent prompts, LangGraph routing, and configuration — not new infrastructure.

### 1.1 Targeted Revision Instead of Full Re-run

**Problem:** When critique scores < 0.7, `prepare_revision` clears all outputs and loops back to `customer_research`. This wastes tokens re-generating sections that scored well.

**Change:** Modify the critique → revision flow to only re-run failing agents.

```python
# Current: always loops back to customer_research
graph.add_edge("prepare_revision", "customer_research")

# New: conditional routing based on which sections failed
def route_revision(state: DiscoveryState) -> str:
    feedback = state.get("critique_feedback", {})
    section_scores = state.get("quality_assessment", {}).get("section_scores", [])
    
    # Find the first section that scored below threshold
    weak_sections = [
        s["section"] for s in section_scores 
        if s["score"] < 0.7
    ]
    
    # Route to the earliest weak agent in the pipeline
    agent_order = [
        "customer_research", "business_strategy", 
        "product_requirements", "technical_architect", 
        "legal_regulatory"
    ]
    
    for agent in agent_order:
        if any(agent in ws.lower().replace(" ", "_") for ws in weak_sections):
            return agent
    
    return "customer_research"  # fallback

graph.add_conditional_edges(
    "prepare_revision",
    route_revision,
    {
        "customer_research": "customer_research",
        "business_strategy": "business_strategy",
        "product_requirements": "product_requirements",
        "technical_architect": "technical_architect",
        "legal_regulatory": "legal_regulatory",
    }
)
```

**Impact:** Saves 40-60% of tokens on revision loops. Faster iterations. Higher quality because agents that scored well aren't disturbed.

### 1.3 Structured Search Grounding

**Problem:** Google Search grounding is enabled globally on agents, but the agents don't construct specific, targeted searches. The LLM decides what to ground.

**Change:** Add explicit search instructions to agent prompts. For the Customer Research agent:

```python
CUSTOMER_RESEARCH_PROMPT = """
...existing prompt...

RESEARCH PROTOCOL:
Before synthesizing your analysis, you MUST ground the following with specific searches:
1. Search for "[product domain] market size [current year]" — cite the source and date
2. Search for the top 3-5 direct competitors by name — extract their pricing, positioning, funding
3. Search for "[target market] pain points survey" or "[industry] customer complaints"
4. Search for recent funding rounds in this space (last 12 months)
5. Search for regulatory news affecting this domain

For EVERY market size figure, growth rate, or competitor claim, include:
- The specific source (company name, report name)
- The date of the data
- Your confidence level (confirmed/estimated/projected)
"""
```

Do the same for Business Strategy (benchmark searches for pricing, revenue multiples) and Legal (specific regulation lookups).

**Impact:** Transforms output from "plausible AI analysis" to "evidence-backed research with citations." This is the single biggest quality multiplier.

## Phase 2: Parallel Execution & Planning Intelligence (2–4 weeks)

**Goal:** Break the sequential bottleneck and add domain-aware intelligence to how the system plans its work.

### 2.1 Parallel Agent Execution

**The Insight:** Looking at your agent data flow, there are real dependencies and artificial ones:

```
REAL dependencies:
  Customer Research → Business Strategy (needs market data)
  Business Strategy → PRD (needs business case for requirements)
  PRD → Technical Architect (needs requirements for architecture)
  All above → Legal (needs full picture)
  All above → Critique (evaluates everything)

ARTIFICIAL dependency:
  Customer Research and Technical Architect are partially independent
  Legal doesn't need Technical Architecture to START — it needs the product concept
```

**Change:** Restructure into two parallel tracks with a convergence point:

```python
from langgraph.graph import StateGraph, END

graph = StateGraph(DiscoveryState)

# Track A: Market & Business (sequential within track)
graph.add_node("customer_research", customer_research_node)
graph.add_node("business_strategy", business_strategy_node)

# Track B: Legal can start early with just the product idea + industry
graph.add_node("legal_preliminary", legal_preliminary_node)  # NEW: early legal scan

# Convergence: These need outputs from Track A
graph.add_node("product_requirements", product_requirements_node)
graph.add_node("technical_architect", technical_architect_node)
graph.add_node("legal_final", legal_final_node)  # NEW: enriched with full context

# Quality gate
graph.add_node("critique", critique_node)

# Track A flow
graph.add_edge("customer_research", "business_strategy")

# Track B starts in parallel with Track A
graph.set_entry_point("parallel_start")
graph.add_node("parallel_start", parallel_start_node)  # fans out

# After both tracks complete, converge
graph.add_node("convergence", convergence_node)

# Post-convergence sequential flow
graph.add_edge("convergence", "product_requirements")
graph.add_edge("product_requirements", "technical_architect")
graph.add_edge("technical_architect", "legal_final")
graph.add_edge("legal_final", "critique")
```

**Implementation with LangGraph's `Send`:**
```python
from langgraph.constants import Send

def parallel_start_node(state):
    return [
        Send("customer_research", state),
        Send("legal_preliminary", state),
    ]
```

**Impact:** Reduces total execution time by 20-30% (legal preliminary runs while research + strategy execute). More importantly, it sets the architectural pattern for Phase 3's full swarm.

### 2.2 Planning Agent (Idea Analyzer)

**Problem:** A fintech payments product and a social media app get the same generic pipeline. The agents don't adapt their depth or focus.

**Change:** Add a lightweight planning step before the pipeline:

```python
graph.add_node("planner", planner_node)
graph.set_entry_point("planner")
graph.add_edge("planner", "parallel_start")

async def planner_node(state: DiscoveryState) -> DiscoveryState:
    """Analyze the product idea and create a research plan."""
    
    planner_prompt = f"""
    Analyze this product idea and create a research plan:
    
    Idea: {state['product_idea']}
    Industry: {state.get('industry', 'Not specified')}
    Target Market: {state.get('target_market', 'Not specified')}
    
    Determine:
    1. DOMAIN_TYPE: [B2B_SaaS | Consumer | Marketplace | Fintech | Healthcare | 
       Hardware | Platform | Other]
    2. COMPLEXITY: [Simple | Moderate | Complex] based on regulatory burden, 
       technical complexity, market dynamics
    3. KEY_RESEARCH_QUESTIONS: List 5-7 specific questions the research agent 
       should answer (e.g., "What is Stripe's market share in SMB payments?")
    4. COMPETITIVE_FOCUS: Name 3-5 specific companies to research
    5. REGULATORY_DOMAINS: List specific regulations to check 
       (e.g., "PCI-DSS", "SOX", "HIPAA")
    6. FINANCIAL_BENCHMARKS: What comparable companies or metrics to use 
       for financial projections
    7. TECHNICAL_CONSIDERATIONS: Key architectural patterns relevant to this domain
    """
    
    plan = await call_llm(planner_prompt, model="gemini-2.0-flash")
    
    state["research_plan"] = parse_plan(plan)
    return state
```

Each downstream agent then receives `state["research_plan"]` and uses it to focus their work. The Customer Research agent uses `KEY_RESEARCH_QUESTIONS` and `COMPETITIVE_FOCUS`. The Legal agent uses `REGULATORY_DOMAINS`. The Business Strategy agent uses `FINANCIAL_BENCHMARKS`.

**Impact:** Dramatically improves relevance. A healthcare product idea will now get HIPAA analysis by default. A fintech idea gets PCI-DSS. The research agent searches for specific competitors, not generic market data.

## Phase 4: Cross-Run Learning & Memory (5–8 weeks)

**Goal:** Make Seedcraft smarter with every run. Implement persistent memory so the system learns what "good" looks like.

### 4.1 Run Memory Store

**Change:** Add a new table and embedding-based retrieval:

```sql
CREATE TABLE run_memories (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES auth.users(id),
    session_id TEXT REFERENCES discovery_sessions(id),

CREATE INDEX idx_memories_embedding ON run_memories

CREATE INDEX idx_memories_quality ON run_memories(quality_score DESC);
CREATE INDEX idx_memories_domain ON run_memories(domain_type, industry);
```

## Phase 5: Swarm Architecture (8–12 weeks)

**Goal:** Full transition to the swarm architecture discussed in earlier conversations. Three parallel agent groupings with intelligent facilitation.

### 5.1 Swarm Definitions

```
DISCOVERY SWARM (parallel)
├── Customer Research Agent (enhanced with memory)
├── Competitive Intelligence Agent (NEW — dedicated competitor deep-dive)
└── Persona Development Agent (NEW — detailed user personas with jobs-to-be-done)

STRATEGY SWARM (parallel, after Discovery converges)
├── Business Case Agent (existing, enhanced)
├── GTM Strategy Agent (NEW — go-to-market split from business case)
└── Financial Modeling Agent (NEW — dedicated projections with benchmarks)

DELIVERY SWARM (parallel, after Strategy converges)
├── PRD Agent (existing sub-workflow)
├── Technical Architect Agent (existing)
├── Legal & Regulatory Agent (existing)
└── Risk Assessment Agent (NEW — cross-cutting risk synthesis)
```

### 5.2 Facilitator Agent

The facilitator replaces the current linear orchestration:

```python
class FacilitatorAgent:
    """
    Central intelligence that:
    1. Creates the research plan (from Phase 2 planner, now enhanced)
    2. Dispatches swarms in parallel
    3. Manages convergence between swarms
    4. Resolves contradictions (e.g., business case assumes X users 
       but research says Y)
    5. Triggers targeted re-runs
    6. Produces the final synthesis
    """
    
    async def run(self, state: DiscoveryState):
        # Step 1: Plan
        plan = await self.create_plan(state)
        
        # Step 2: Discovery Swarm (parallel)
        discovery_results = await asyncio.gather(
            customer_research_agent.run(state, plan),
            competitive_intel_agent.run(state, plan),
            persona_agent.run(state, plan),
        )
        
        # Step 3: Convergence check
        discovery_synthesis = await self.synthesize_discovery(discovery_results)
        contradictions = await self.detect_contradictions(discovery_synthesis)
        
        if contradictions:
            # Targeted re-run of conflicting agents
            discovery_results = await self.resolve_contradictions(
                contradictions, discovery_results
            )
        
        # Step 4: Strategy Swarm (parallel)
        strategy_results = await asyncio.gather(
            business_case_agent.run(state, discovery_synthesis),
            gtm_agent.run(state, discovery_synthesis),
            financial_agent.run(state, discovery_synthesis),
        )
        
        strategy_synthesis = await self.synthesize_strategy(strategy_results)
        
        # Step 5: Delivery Swarm (parallel)
        delivery_results = await asyncio.gather(
            prd_agent.run(state, discovery_synthesis, strategy_synthesis),
            architect_agent.run(state, strategy_synthesis),
            legal_agent.run(state, discovery_synthesis, strategy_synthesis),
            risk_agent.run(state, discovery_synthesis, strategy_synthesis),
        )
        
        # Step 6: Final critique and synthesis
        pack = await self.create_inception_pack(
            discovery_synthesis, strategy_synthesis, delivery_results
        )
        
        return pack
```

### 5.3 Contradiction Resolution

The most valuable capability of the facilitator:

```python
async def detect_contradictions(self, results: dict) -> list[Contradiction]:
    """
    Examples of contradictions to detect:
    - Research says TAM is $500M, but Business Case projects capturing 
      $100M (20% market share for a startup — unrealistic)
    - Research identifies enterprise as target, but GTM strategy 
      proposes a self-serve PLG motion
    - PRD has 25 user stories but Technical Architect proposes 
      a 6-month MVP timeline
    - Legal flags HIPAA requirements but Architecture has no 
      encryption at rest
    """
    
    prompt = f"""
    Review these agent outputs for internal contradictions:
    {json.dumps(results, indent=2)}
    
    Look for:
    1. Numeric inconsistencies (market sizes, user projections, timelines)
    2. Strategic misalignment (target market vs GTM approach)
    3. Scope vs timeline mismatches
    4. Compliance gaps (legal requirements not reflected in architecture)
    5. Assumption conflicts between agents
    """
    
    return await call_llm(prompt, model="gemini-2.5-pro")
```

## Summary: Priority & Sequencing

| Phase | Effort | Impact | Key Metric |
|-------|--------|--------|------------|
| **Phase 1:** Surgical improvements | 1-2 weeks | High | Quality scores improve 10-15% |
| **Phase 2:** Parallel execution + planning | 2-4 weeks | High | Execution time drops 30%, relevance improves significantly |
| **Phase 3:** Rich visual output | 3-5 weeks | Very High | User engagement, "wow factor," stakeholder usability |
| **Phase 4:** Cross-run learning | 5-8 weeks | High (compounds) | Quality improves with each run, convergence to 0.85+ avg |
| **Phase 5:** Full swarm | 8-12 weeks | Transformative | New product category, deeper analysis, contradiction detection |

### Recommended Order

**Start with Phase 1** — it's all prompt and config changes, no new infrastructure. You can ship it in a week and immediately see better outputs.

**Then Phase 3** — rich output is what users see. Even if the underlying analysis doesn't change, interactive charts and visual artifacts make the product feel 10x more professional. This is what sells.

**Then Phase 2** — parallel execution and planning intelligence. This requires LangGraph changes but the patterns are well-documented.

**Phase 4 before Phase 5** — memory/learning is the foundation that makes swarms effective. Without cross-run learning, adding more agents just adds more mediocre output. With it, every agent gets progressively smarter.

**Phase 5 last** — the swarm architecture is the end goal but requires all the preceding infrastructure to work well.
